MongoDB sigue sin implementarse, la documentación señala expresamente que MongoDB queda fuera del alcance de este parcial, sin embargo, los lineamientos solicitaban almacenamiento real, incluyendo inserción, consulta, actualización, filtrado, agregaciones, índices y recuperación mediante identificadores relacionados. Deben de incorporar MongoDB como parte funcional del simulador, por ejemplo para almacenar resultados extensos de corridas, series temporales, historial de parámetros, salidas de algoritmos o eventos semiestructurados, además, deberán explicar qué información corresponde a PostgreSQL y qué información corresponde a MongoDB. No es suficiente instalar el contenedor de MongoDB ni agregar una conexión sin operaciones reales.

Dependencia de reglas de negocio compartidas con el monolito, los microservicios reutilizan módulos de backend_web, lo que permite aprovechar lógica existente, pero introduce riesgos de acoplamiento. Si un cambio en el backend monolítico obliga a modificar simultáneamente varios servicios, la arquitectura pierde parte de su independencia, por lo que deben de establecer propietarios claros de las reglas de negocio, separar contratos de dominio y demostrar despliegues independientes. La biblioteca común debería concentrarse en funciones técnicas compartidas, no convertirse en una vía para acoplar todos los servicios al monolito.

Hace falta validación científica del simulador, este es el problema más importante desde el punto de vista del propósito del proyecto. La plataforma puede crear escenarios, ejecutar simulaciones y generar resultados, pero para ofrecer información útil para salud pública debe demostrar que sus modelos epidemiológicos son matemáticamente consistentes y que sus resultados pueden interpretarse adecuadamente, que debe de presentar pruebas de sensibilidad de parámetros, reproducibilidad de corridas, validación frente a resultados esperados y una descripción de los supuestos y limitaciones. Deben distinguir claramente entre simulaciones exploratorias, predicciones y resultados validados. La visualización de una curva no demuestra por sí misma que el modelo sea epidemiológicamente correcto.

Veo pruebas documentadas, pero no completamente cerradas, el reporte reconoce una prueba fallida en una ejecución global, atribuida a migraciones de una base de datos de pruebas desactualizada, también identifica pendientes relativos a validación de ejemplos de contratos y documentación complementaria, por lo que deben de ejecutar todas las pruebas sobre una base inicializada desde cero, consolidar el resultado final y entregar evidencia de una suite completa sin errores inesperados. No deben presentar pruebas de distintas versiones como si correspondieran a una sola ejecución.

Hay evidencias de interoperabilidad pendientes, aunque existen contratos JSON/XML y esquemas XSD, el checklist todavía señala que deben revisarse algunos ejemplos y validaciones, deben corregir y demostrar que las aplicaciones cliente pueden consumir contratos reales sin depender de clases internas, código compartido del servidor o conexiones directas a PostgreSQL. Las pruebas deberán cubrir datos válidos, inválidos, respuestas de error, permisos, versiones y XML contra XSD.

Falta una demostración operativa de usuarios finales y la consola de pruebas es una herramienta adecuada para desarrolladores, pero no sustituye la experiencia de un epidemiólogo o analista. Hay que demostrar un proceso completo mediante una interfaz de usuario que permita comprender, configurar, ejecutar y comparar escenarios sin requerir conocimientos de programación, el sistema debe mostrar progreso, errores comprensibles, resultados visuales, supuestos y limitaciones del modelo.

Recuerden que la participación individual y separación entre grupos y no veo exactamente que hizo el otro equipo y que hicieron ustedes, deben definir exactamente que hizo cada equipo y diferenciar las entregas, así como lo entregan dificultan atribuir responsabilidades si no se documentan las contribuciones, deben de entregar una matriz individual de autoría y participación que identifique servicios implementados, pruebas, integración, documentación, incidencias y correcciones realizadas por cada estudiante. Durante la defensa técnica deberán poder ejecutar, explicar y modificar el código de los componentes bajo su responsabilidad.

Recomiendo exigir una demostración con un escenario epidemiológico ficticio de Nuevo León, utilizando datos de prueba y parámetros documentados. La prueba deberá incluir la configuración de una enfermedad, población, escenarios alternativos e intervenciones sanitarias. Posteriormente, el sistema tendrá que ejecutar corridas, almacenar resultados, construir indicadores y comparar alternativas.

Demostración integrada obligatoria

1. Un analista inicia sesión y obtiene un JWT validado mediante Redis.

2. Selecciona una enfermedad, región, población y parámetros epidemiológicos.

3. Crea dos escenarios: uno sin intervención y otro con medidas sanitarias.

4. El sistema valida y registra los escenarios en PostgreSQL.

5. Un epidemiólogo autorizado aprueba las versiones correspondientes.

6. Se solicitan dos corridas y se procesan mediante el motor de simulación.

7. Los resultados extensos se almacenan en MongoDB y se relacionan con las corridas de PostgreSQL.

8. El usuario consulta curvas, indicadores y resultados en la aplicación web.

9. Se comparan las alternativas considerando consecuencias epidemiológicas y costos definidos en el modelo.

10. Se presenta una frontera de Pareto cuando existan objetivos y resultados adecuados para calcularla.

11. Se comprueba el funcionamiento de las APIs mediante JSON/XML, Swagger y XSD.

12. Se fuerza un fallo controlado de un servicio y se verifica la recuperación sin duplicar corridas ni perder resultados confirmados.

SIGUIENTE ENTREGA

El equipo deberá evolucionar EPIDEMIA hasta convertirlo en una plataforma integral de vigilancia epidemiológica, simulación y apoyo a la toma de decisiones en salud pública, que permita a sus usuarios trabajar desde tres aplicaciones:

- Aplicación web: administración regional, vigilancia, campañas, mapas epidemiológicos, indicadores, reportes y seguimiento de intervenciones.

- Aplicación móvil Android (JSON): captura de casos en campo, seguimiento epidemiológico, consulta territorial, notificaciones y sincronización de información.

- Aplicación de escritorio (XML): configuración de modelos, diseño y ejecución de escenarios, simulaciones, comparación de estrategias, análisis de sensibilidad y evaluación de decisiones.

La entrega actual reúne 26 microservicios desarrollados por dos grupos, pero presenta tres limitaciones importantes que deberán resolverse prioritariamente: MongoDB no está integrado funcionalmente; el sistema web todavía no consume los microservicios; y falta demostrar la validez epidemiológica de los modelos de simulación. No recomiendo que los alumnos comiencen simplemente agregando más servicios. Primero deberán completar la integración y demostrar un proceso funcional de principio a fin. Después podrán ampliar la arquitectura para incorporar funciones avanzadas de vigilancia, modelado y evaluación.

Microservicios existentes que deben completarse y fortalecerse

Las responsabilidades actuales incluyen identidad, usuarios, catálogos, vigilancia, escenarios, simulación y análisis. Para que puedan proporcionar servicios completos a Android, escritorio y web, deberán ampliarse como sigue.

Estos servicios deberán organizarse conforme a límites funcionales reales. Por ejemplo, calibracion-modelos y validacion-cientifica podrían ser módulos especializados de un mismo servicio de investigación y modelado si comparten las mismas dependencias y ciclo de despliegue. El requisito más importante es la validación científica, los CDC destacan que la utilidad de los modelos epidemiológicos depende de su adecuación al problema, calidad de las entradas, validación contra observaciones y tratamiento de la incertidumbre. Un modelo más complejo no necesariamente produce mejores resultados, por lo tanto, cada modelo desarrollado deberá contar con una ficha que indique su formulación matemática, población representada, variables, supuestos, fuentes de parámetros, límites de aplicación, versión del algoritmo, escenarios de prueba y resultados de validación.

APLICACIÓN MÓVIL ANDROID

La aplicación Android debe estar diseñada para capturistas epidemiológicos, personal de vigilancia, supervisores regionales y responsables de campañas autorizadas. No debe limitarse a mostrar las gráficas de la aplicación web ni convertirse en una versión reducida del simulador. Su función será recolectar, verificar y sincronizar información de campo que alimente los procesos epidemiológicos.

Módulo y funcionalidades: 

Inicio de sesión: JWT, renovación, almacenamiento seguro de credenciales, bloqueo y cierre de sesión.

Panel del capturista: Casos pendientes, formularios, registros incompletos, sincronizaciones pendientes y avisos.

Registro de casos: Captura de fecha epidemiológica, enfermedad, región, clasificación, datos autorizados y validaciones.

Seguimiento: Actualización de estados, observaciones, historial y resultados autorizados.

Geolocalización: GPS para registrar la ubicación pertinente con autorización; selección manual cuando no sea adecuada la captura automática.

Formularios dinámicos: Campos definidos por enfermedad, versiones de formularios, validaciones y datos obligatorios.

Evidencias: Fotografía o documentos cuando el protocolo lo autorice, con almacenamiento seguro.

Sincronización offline: Captura de borradores, cola local cifrada, control de duplicados, conflictos y confirmación del servidor.

Consulta epidemiológica: Información agregada por zona, periodo y enfermedad según los permisos del usuario.

Alertas: Notificaciones de nuevas tareas, registros rechazados, campañas y eventos de vigilancia.

Control de calidad: Advertencias por campos incompletos, fechas incoherentes y registros potencialmente duplicados.

Perfil: Identificación del usuario, institución, región asignada y estado de conexión.

Recomiendo desarrollar Android en Kotlin con Jetpack Compose y una arquitectura MVVM o equivalente. Deberá consumir exclusivamente APIs JSON sobre HTTPS y utilizar almacenamiento local cifrado para los datos permitidos. El sistema deberá prevenir la duplicación cuando el usuario reenvíe un registro, pierda conectividad o cierre inesperadamente la aplicación. La regla obligatoria es que un registro capturado offline no deberá considerarse recibido, validado o publicado hasta que el servidor lo confirme. Además, la sincronización no debe sobrescribir silenciosamente información modificada por otro profesional.

APLICACIÓN DE ESCRITORIO

Esta aplicación será el componente especializado de mayor importancia para el proyecto. Debe proporcionar un entorno profesional que permita a un epidemiólogo o analista construir modelos y evaluar estrategias sin escribir código ni interactuar directamente con PostgreSQL. El escritorio consumirá XML mediante APIs REST, validará las respuestas con XSD y podrá utilizar WebSockets o SSE para recibir el progreso de las simulaciones. El canal de progreso debe documentarse de forma independiente de los contratos XML.

Módulo y funcionalidades: 

Administración de proyectos: Crear investigaciones, seleccionar región, enfermedad, periodo y modelos.

Gestión de datos: Importar conjuntos autorizados, verificar calidad, examinar series y registrar versiones.

Configuración del modelo: Seleccionar SEIR u otro modelo implementado, ajustar parámetros y visualizar definiciones y unidades.

Editor de escenarios: Crear, duplicar, editar y versionar escenarios de referencia e intervención.

Configuración de intervenciones: Definir fecha de inicio, duración, cobertura, intensidad y costos.

Calibración: Ajustar parámetros con series históricas y comparar los resultados de ajuste.

Validación: Ejecutar escenarios de prueba, análisis de sensibilidad y comprobación de restricciones matemáticas.

Ejecución de simulaciones: Iniciar, cancelar, monitorear y recuperar corridas asíncronas.

Comparación: Visualizar escenarios simultáneos, diferencias, incertidumbre y métricas epidemiológicas.

Análisis económico: Evaluar costos bajo supuestos explícitos y comparar costo-efectividad exploratoria.

Análisis Pareto: Identificar alternativas no dominadas según objetivos comparables y documentados.

Mapas regionales: Mostrar distribución geográfica, intensidad e indicadores por zona.

Reportes: Exportar resultados, parámetros, versiones, gráficas, metodología y limitaciones.

Reproducibilidad: Guardar semilla, versión del modelo, datos, parámetros y condiciones para repetir una corrida.

Auditoría: Consultar quién creó, modificó, revisó o aprobó cada escenario.

La aplicación debe permitir seleccionar cada curva, consultar el escenario que la produjo, examinar sus supuestos y reproducir la corrida. Las gráficas no podrán mostrarse sin identificar fuente, periodo, modelo, versión y unidades. MongoDB deberá incorporar referencias estables al run_id, scenario_id y a la versión del modelo almacenadas en PostgreSQL. Los resultados no deben quedar desconectados de la corrida que los produjo. Una corrida deberá conservar los parámetros exactos, identificador del dataset, versión del algoritmo, semilla aleatoria cuando aplique, fecha de ejecución, resultados y estado final. Para los trabajos asíncronos, el equipo deberá probar qué ocurre si un worker se detiene después de guardar resultados pero antes de confirmar que terminó el trabajo. El sistema debe evitar corridas duplicadas y recuperar estados de forma consistente.

Para poder tener el sistema aceptable, deben de:

Captura móvil: Registrar casos de prueba desde Android, con datos válidos e inválidos.

Sincronización offline: Guardar registros sin Internet y sincronizarlos sin duplicados.

Integración del portal web: Comprobar que una operación web consume realmente una API.

Autorización: Impedir que un capturista modifique escenarios de otra institución.

Escenario de referencia: Crear y versionar un escenario sin intervención.

Escenario alternativo: Configurar intervenciones con fechas, intensidad y duración.

Validación matemática: Rechazar parámetros epidemiológicos imposibles o incoherentes.

Reproducibilidad: Repetir una corrida determinista con las mismas condiciones y obtener el mismo resultado.

Modelo estocástico: Reproducir una ejecución usando la misma semilla y versión.

Sensibilidad: Variar parámetros y comprobar el comportamiento esperado del modelo.

Persistencia: Recuperar resultados relacionados entre PostgreSQL y MongoDB.

Comparación: Comparar escenarios bajo una misma línea base y métricas.

Incertidumbre: Mostrar intervalos o distribuciones apropiadas, con su interpretación.

Fallo de worker: Interrumpir una corrida y recuperarla sin duplicar resultados.

Contratos: Consumir JSON en Android y XML/XSD en escritorio.

Prueba de usuarios: Completar tareas sin ayuda de los desarrolladores.

Para la prueba de usabilidad, recomiendo contar con usuarios representativos de tres perfiles: capturista de campo, epidemiólogo y analista de simulación. De ser posible, deben incluirse al menos cinco participantes por perfil para identificar problemas iniciales de interacción; esta muestra no sustituye una validación científica o estadística más amplia.
