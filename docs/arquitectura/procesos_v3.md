# Los tres procesos de la v3, paso a paso

Es el paso 2 del orden de trabajo de [`brechas_v3.md`](brechas_v3.md) (§11): los tres procesos integrales que pide la rúbrica, escritos con la tabla de §10.1. De aquí salen después las matrices y el inventario de datos (§10.2 y §10.3).

Cómo leer las tablas:

- Cada renglón es un paso del proceso **como debe quedar en la v3**. Lo que hoy existe se describe como está en el código (revisado el 2026-11-11).
- **Falta (ID):** el paso o la pieza no existe; el ID es su brecha en `brechas_v3.md`.
- **Propuesta:** una forma de cerrar una brecha que el equipo todavía no ha decidido.
- **RF:** el ID del requerimiento viejo (`requerimentos/funcionales/rf-*.md`, marcados como Obsoletos) que corresponde al paso, como pide §10.1. «Nuevo (D)» es un paso sin RF que pide uno nuevo del módulo D; se numera al redactar los requerimientos (§10.6).
- **Formato:** JSON en la móvil, XML en el escritorio y HTML en la web, que va directo a PostgreSQL (D20). Entre servicios es JSON.
- **Escribe en** y **Lee de:** PG es PostgreSQL. «Teléfono» es lo que la app guarda localmente.

## Preguntas para validar en equipo

1. **P1, notificación:** ¿a quién se avisa y cuándo? La propuesta es un aviso por lote a los EPIDEMIOLOGO cuando trae casos nuevos, no uno por caso.
2. **P1, actualización (C9):** ¿basta con aplicar dosis y marcar avisos, o se agrega editar un caso pendiente antes de mandarlo?
3. **P2, archivo en GCS:** ¿el XML de intercambio es el archivo de P2, o P2 se queda sin bucket?
4. **P3, MongoDB:** ¿la serie diaria de cada corrida pasa de `simulation_results` a MongoDB (D28)? Es el candidato más claro para D-1 y para el volumen de D-6.
5. **P3, réplicas (D8):** el escritorio ya resume en el cliente. ¿Se confirma así o el resumen pasa a un servicio?
